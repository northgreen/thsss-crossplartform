# Math baseline investigation (2026-10-31)

This is an audit fixture and solution-prototype check, not a production regression suite. Production math still differs from the historical data. Do not add this suite to game regression runners or change production math/game logic to make this audit green.

- `Probe.cs` records bit patterns for CLR math, SlimDX vectors/matrices, direct movement and trajectories. `MathBaseline.csproj` runs it against current .NET 8 and the project compatibility types.
- `ActualProbe.cs` invokes shipped/current `Shooting.BaseObject` methods through reflection without constructors or gameplay. `ActualProbe.csproj` accepts assembly, output CSV and input paths.
- The six compressed CSVs are actual Windows CLR2 x86 captures: default x87 53-bit significand precision and post-original-D3D9-CreateDevice 24-bit precision (`-d3d`). A newly started managed worker in that same process was measured at 53 bits. Do not conflate these states or add `FpuPreserve` to the capture flags.
- `inputs.bin` is 4096 little-endian `(double, double, float, float)` records, 98304 bytes, SHA256 `6bd574af15179cca05f8f249ae0bd8218b22a82ddd01c0b3cd506c00b5a2ba6d`.
- Raw historical data must never be regenerated from modern outputs. Preserve bytes when compressing (`gzip` mtime zero, no embedded filename). New legacy captures go to a separate output directory for review, not over the golden files.
- `compare.py` reports bit differences and ULP distances between two uncompressed CSVs; differences are audit findings, not automatic production test failures. It includes groups such as pow/parse that the solution prototype does not claim to solve.
- `baseline.json` binds original binaries, runtime/CPU identity, precision states, input and each raw CSV SHA256/size/row count. `sh verify.sh` checks these fixture identities and builds only `SolutionsProbe.csproj` and the investigation-only native shim in a unique temporary directory. Linux x86_64 is required; other platforms fail explicitly. Both precision modes must check 473728 samples with zero differences before `MATH_BASELINE_SOLUTIONS_PASS`. This demonstrates candidate behavior on retained inputs, not universal math parity or a production fix.
- `legacy_x87.c` restores the caller's x87 control word after each operation. It is a Linux x86_64 investigation shim, not a portable production library.
- `RandomProbe.cs` invokes actual game `MyRandom(0)` with an identical 10000-cycle mixed call sequence. `LegacyRandomModel.cs` preserves the captured integer algorithm plus precision-sensitive scaling and `ranValue` bookkeeping. Seeded integer sequences alone do not prove post-D3D floating Random compatibility.
- `capture-legacy.ps1 -RepoRoot <repo> -OutputDir <capture-root> [-D3dx9Dll <app-local-dll>]` requires an already installed Windows CLR2 x86 compiler/runtime and original `reference/original/{SlimDX.dll,THSSS.exe}`. It compiles into a unique temp directory and retains CSVs, input digest, binary/source hashes and metadata in a fresh output subdirectory. It installs no OS features or dependencies.
- D3D capture must run in an interactive Windows desktop, not SSH/session 0. No adapters is a failure, never a skip. `D3dProbe.cs` creates a real D3D device with the original flags, then invokes both probes on the same STA thread/process; standalone launches cannot reproduce that precision state.
- Never include credentials, private machine paths, CLR/D3DX binaries or installers in this suite. Supply optional app-local D3DX9 externally. Do not alter VM/runtime resources during consolidation.
